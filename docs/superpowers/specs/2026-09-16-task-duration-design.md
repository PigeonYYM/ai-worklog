# 流水时长记录设计

2026-09-16

## 背景

现有流水只记「什么时候完成了什么」，不记「花了多久」。填工时需要逐条时长，
事后靠回忆估算既不准也费事。

目标是让每条流水自带时长，并能按项目、按天汇总出可直接填报的小时数。

## 非目标

- **不回填历史数据。** `.raw/` 里 2026-03 至今的流水全是 4 列，时长信息在当时
  根本没有被采集过，任何回填都是编造数字——对填工时来说比留空更糟。
- **不做时长封顶。** 用户明确要求如实记录，长时间无人值守的跨度照实写入，
  填报时由人自行分配。封顶只用于识别孤儿标记（见「未知语义」）。
- **不改变流水的 append-only 语义**，也不改变「md 是纯派生产物」的前提。

## 方案选择

考虑过三条路：

1. **会话内标记点差值**（采纳）——每个工具在会话内维护「上次记录时刻」，
   每写一条流水取差值并推进标记。
2. **任务生命周期配对**——`PreToolUse` 抓 `TaskUpdate status=in_progress` 作起点，
   `TaskCompleted` 作终点，用 `task_id` 关联。
3. **不改格式，整合时按相邻记录间隔推导**。

选 1 的决定性理由是**总和守恒**：一个会话内各条时长之和恰好等于该会话的真实
流逝时间，不重不漏。这正是工时填报需要的性质。

2 的语义更准（「真正干这件事的时间」），但只有 Claude 有任务概念，codex 与
opencode 仍需回退到 1，等于维护两套机制；且多任务并发 in_progress 会重复计时，
任务之间的探索与 review 时间不归属任何一条，导致当天合计显著小于实际工时。

3 是唯一能回溯历史的方案，但三个工具的记录交错在同一份流水里，间隔失去意义；
更致命的是 opencode 由整合任务批量补写，时间戳是过去的，算出的间隔纯属噪音。

## 数据格式

TSV 由 4 列扩展为 5 列：

```
时间 \t 项目 \t 标题 \t 来源工具 \t 时长秒
09:12	overseas-ad-scheduler	接入 Google Ads 转化回传	claude	4260
```

**存整数秒而非分钟。** 用户要求如实记录，秒是原始精度，不应在写入时就丢失；
且大量短记录求和时，逐条取整到分钟会累积可观误差。展示层再换算成小时。

**未知写空字符串，不写 0。** `0` 表示「确实没花时间」，空表示「不知道」，
两者在汇总时必须能区分，否则未知会被当作零工时静默吞掉。

## 标记点机制

`worklog.py` 增加共享的标记读写层，标记文件位于
`~/daily-report/.state/marks/<工具>-<会话>.mark`。

放 `.state/` 而不是 `/tmp`：排障时可直接查看，也不会被系统临时目录清理策略
影响。需要配套的过期清理，沿用 `codex_prompt.cleanup_stale` 的既有写法。

三个工具的起点来源：

| 工具 | 起点 | 改动 |
|---|---|---|
| Claude | 新 `UserPromptSubmit` hook 写标记；每条 `TaskCompleted` 取差值后把标记推进到当前时刻 | 新增 `claude_prompt.py`，`settings.json` 加一个 hook |
| codex | 已有 —— `codex_prompt.py` 写的缓存文件 mtime 即 turn 起点 | `codex_stop.py` 取 mtime 算差值 |
| opencode | `session` 表的 `time_created` | SELECT 补一列，时长取增量跨度（见下） |

Claude 是唯一需要新 hook 的链路。一个 turn 内完成多个任务时，标记逐条推进，
因此各条时长之和等于该 turn 的真实耗时。

opencode 的粒度天然是**整个会话**，其时长可能横跨数小时或隔夜。这由它的数据
模型决定，无法做得更细。

**opencode 必须取增量跨度。** 采集水位线走 `time_updated`：续用一个旧会话会
使其 `time_updated` 前移，该会话因而被再次采集。若此时按
`time_updated - time_created` 计算，同一段时间会被重复计入工时。

正确算法是用水位线截断起点：

```
时长 = time_updated - max(time_created, 上次采集水位线)
```

首次采集时水位线早于创建时刻，取 `time_created`，即完整跨度；续采时取水位线，
只计入本次新增的那段。这样跨多次采集的累加值仍等于会话总跨度，总和守恒不被破坏。

## 未知语义

以下情况时长记为空：

- 标记文件不存在（hook 未触发、会话早于本功能上线）
- 标记文件的时间戳距今超过 24 小时——视为孤儿，写入一个「3 天」级别的数字
  没有意义。这是脏数据识别，不是对正常时长的封顶。

## 展示

**数字不交给模型计算。** 日报正文由 `kimi-for-coding/k3` 归纳，若让它一并汇总
时长，数字会被揉进自然语言，一旦被改动无从察觉。因此职责拆分：

- 模型只负责文字归纳。prompt 中带上时长，并明确要求原样保留、不做加总。
- `summarize.py` 在模型正文之后，以脚本确定性地追加「工时」小节：按项目汇总
  小时数与当天合计。

这样即便模型退化为脚本渲染，工时小节完全一致。现有三条硬性校验无需改动。

新增 `--hours` 模式，直接输出填报口径而不生成 md：

```bash
/usr/bin/python3 ~/worklog/summarize.py --hours --since 2026-09-14
```

## 兼容

- `read_day` 同时接受 4 列与 5 列，4 列的时长解析为 `None`。
- `append_record` 新增时长参数并带默认值，签名向后兼容。
- 历史数据保持原样，渲染时不显示时长。

## 测试

按 TDD 推进，全部通过 `WORKLOG_HOME` 重定向到临时目录，不触碰真实
`~/daily-report/`。

新增覆盖：

- 标记点的写入、取用、缺失、过期四条路径
- 三个工具各自的时长计算
- `read_day` 混读 4 列与 5 列
- 工时汇总的加总正确性（含未知条目不被当作 0）
- opencode 续用会话被二次采集时，两条记录的时长之和等于会话总跨度
- `--hours` 输出格式

## 风险

**改 `~/.claude/settings.json`。** 2026-09-11 那次改造为此做过备份、`jq` 校验与
全字段比对。本次沿用同样流程：先备份，改动后逐字段比对，确认仅 `UserPromptSubmit`
一个键发生变化。

**新 hook 在每次回车时执行。** 因此 `claude_prompt.py` 只写一个时间戳文件，
并配置为 `async`，避免给交互增加延迟。
